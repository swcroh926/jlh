## 최신 작업 — 기능명세 적용 시작 (2026년 11월 18일)

사용자 제공 명세 원문은 `docs/FUNCTIONAL_SPEC_v1.1.md`, 항목별 비교와 추가 작업 순서는 `docs/SPEC_GAP_ANALYSIS.md`에 보관합니다. 사용자는 원본 주제 수를 **최대20개**로 확정했습니다. 원문의 15개 표기는 원본 보존을 위해 그대로 두고 결정 내용을 비교 문서에 기록했습니다.

기존 기능은 보존하고 첫 작업인 **학생 조건·기본값·주제 입력 정비**를 완료했습니다. 브랜치 `feature/spec-v11-inputs`에서 로컬 검증했으며, main 병합/공개 배포/유료 AI 호출은 하지 않았습니다. 아래 과거 구현 상태에서 달라지는 부분은 이 최신 작업과 비교 문서를 우선 참고하세요.

완료:

- 이름/별명·학년·지역 필수, 예산 미입력/0원 구분, 선생님 기본 30만 원·8주·주1회3시간·학원. 새 기본값을 기존 프로젝트에 자동 적용하지 않습니다.
- 지역·이름을 AI 요청에서 제외하고 회당 시간·장소·장비를 검증/평가 입력·캐시 키에 포함합니다.
- 직접/TXT/DOCX/HWPX 입력, 원본 최대20개 검증, 완전 동일 주제 안내, 초과 주제를 임의로 자르지 않는 처리, 추출 미리보기·수정·추가/교체/취소·최종 확정.
- 확정한 원본 표현·고유 ID 보존, 구버전 브라우저 데이터 이전, 이전 프로젝트 보관/복원, 기존 실험 기록 유지, 조건 변경 시 이전 평가/계획 재검토 표시.
- HWP 변환 도구가 있으면 시간 제한을 두고 시도하고, 미설치/실패 시 HWPX/DOCX/TXT 변환 안내.

검증:

- 프런트엔드 14개, Python 백엔드 41개 테스트 통과.
- 실제 로컬 서버에서 합성 DOCX/HWPX를 추출하고 Playwright로 기본값/0원/20개초과/중복/취소/추가/교체/확정/기록복원/프로젝트보관/구버전이전/재검토/개인정보 제외/모바일을 검증했습니다.
- 브라우저의 평가 요청은 테스트 응답으로 대체했고 실제 OpenAI/Gemini 호출은 하지 않았습니다. 기존 공개 사이트에 반영된 검증과 구분합니다.
- 실제 HWP 파일 변환 성공은 미검증입니다. 이 환경에 hwp5txt를 설치하지 않았고 분기만 모의 검증했습니다. 실제 교실 문서의 복잡한 표/레이아웃은 샘플로 추가 검토해야 합니다.

첫 단계 완료 당시 남은 순서: Find_Interest → Check_Duplicate → 5항목 가중 Eval_Topic·80점 이상·실행 가능/위험 보류 → Create_Topic·1회 재평가 → Set_Exp·비용/일정·확정 → 서버 프로젝트/버전 저장 및 품질 검증. 생성 후보 상한(원본20+생성10과 내부25)의 충돌은 생성 단계에서 별도 규칙을 확정해야 합니다. 현재 기본값·프로젝트 기록의 저장 위치는 브라우저이며 서버 프로젝트 저장까지 완료한 것은 아닙니다.

## 다음 작업 완료 — Find_Interest (2026년 11월 18일)

같은 브랜치 `feature/spec-v11-inputs`에서 두 번째 작업을 구현했습니다. 사용 방법·API 계약·검증 방법은 `docs/FIND_INTEREST.md`에 있습니다. 공개 배포와 실제 유료 모델 호출은 하지 않았습니다.

- 원본 주제만 대상으로 AI 분류 초안과 선생님 직접 분류를 지원합니다. 이름·지역 등 프로필 필드는 분석 요청에서 제외합니다.
- 물리·화학·생물·산업 및 에너지(SW/IT)·지구 및 환경의 복수 영역과 구체적 관심 주제, 근거 원본 ID, 불확실성을 표시합니다.
- 주제당 중복 근거를 제거하고 개수/비율과 영역별 합집합을 서버가 계산합니다. 반복 단어 수를 세지 않습니다. 생성 주제를 원본 분석에 넣으면 서버가 거절합니다.
- 교사 수정·확정·불확실성 이유를 남긴 미정 확정이 가능합니다. 직접 경로는 API 호출이 없습니다. AI 경로는 비용 확인을 거친 명시적인 버튼 실행만 허용합니다.
- 분류 수정 중에는 실제 AI 평가를 비활성화하고, 확정 후에는 서버가 저장된 버전을 다시 읽어 관심도 평가에 전달합니다. 이전 평가/계획/노트는 지우지 않습니다.
- 원본 변경·관심사 변경 시 재검토와 평가 캐시 무효화를 적용합니다. 생성 주제 추가만으로 관심사 원본/분모가 바뀌지 않습니다.
- .local/interests.sqlite3에 AI 초안과 교사 확정/수정 버전, 부모 버전, 모델·기준·사용량·생성 시각을 저장합니다. 브라우저에는 프로젝트 연결과 수정 중 내용을 저장합니다. 전체 서버 프로젝트 저장은 후속 작업입니다.
- 평가 지침이 확정 관심사 프로필을 참고하도록 바뀌어 루브릭 버전을 science-title-evaluation-v1.1-interests로 갱신했습니다. 항목/가중치는 아직 기존 4항목 기준입니다.
- 백엔드 55개·프런트엔드 21개 자동 테스트와 입력 단계 회귀/관심사 단계 브라우저 테스트를 통과했습니다. 브라우저 모델은 테스트 전용 서버의 모의 응답이며 실제 HTTP·SQLite·서버 검증·계산·화면과는 구분합니다.
- 검증에는 잘못된 근거 ID/모델 형식 미저장, 초안 평가 거절, 교사 수정의 이전 버전 보존, 새로고침·서비스 재생성 후 복원, 평가 캐시 분리, 직접 분류의 키 미사용, 비율 반올림 경계, 모바일 가로 넘침을 포함했습니다.

남은 한계: 실제 모델의 관심사 분류 품질은 아직 검증하지 않았고, Gemini/로컬 모델로 전환하지 않았습니다. 기존 OpenAI API 어댑터를 재사용합니다. 다음 개발은 `Check_Duplicate`의 위험 상태·공통점·차이·검사 미완료·교사 검토 계층입니다.

## 개발본 직접 테스트 지원 (2026년 11월 18일)

- 사용자가 개발 중간에 직접 테스트하는 방법을 요청해 `START_LOCAL.bat`와 `docs/TESTING_FOR_TEACHERS.md`를 추가했습니다.
- Windows에서 Python을 감지하고 저장소 폴더에서 서버를 실행한 뒤 브라우저를 엽니다. 항상 127.0.0.1:8012를 사용해 브라우저 기록의 주소를 일정하게 유지합니다.
- 배치 실행 프로세스 안에서만 API 키를 비워 유료 호출을 비활성화합니다. 기존 전역 환경 변수나 Codex 시크릿을 수정하지 않습니다.
- 개발 브랜치 ZIP 다운로드, 새 버전 덮어쓰기, `.local`과 브라우저 기록 보존, 직접 관심사 분류·파일 입력·검색·기록 확인, 피드백 전달 순서를 안내했습니다.
- `backend.server --open-browser` 옵션과 실제 바인딩된 주소 출력을 추가했습니다. 포트 사용 중이면 다른 앱을 자동 종료하지 않고 안내합니다.
- 검증: Python 서버 통합 테스트 55개 통과. 별도 프로세스에서 실제 임의 포트 HTTP/health 응답·키 미등록·브라우저 열기 콜백의 준비된 주소를 확인했습니다. 배치 파일의 CRLF/프로세스 한정 키 비활성화를 확인했습니다. Windows에서 실제 두 번 클릭한 검증은 아직 아닙니다.
- 무료·수동 기능 테스트 경로이며 실제 모델 품질 검증이나 공개 배포를 한 것은 아닙니다.

## PC에서 실제 AI 관심사 분석 실행 지원 (2026년 11월 18일)

- 기존 관심사 분석 API는 OpenAI 어댑터에 연결돼 있지만 무료 START_LOCAL.bat에서는 꺼집니다. 사용자가 실제 AI를 붙여 테스트하는 방법을 요청해 START_AI_LOCAL.bat와 backend/ai_preview.py를 추가했습니다.
- 비용 동의(YES) 후 터미널 getpass로 키를 숨김 입력하고, 실행 프로세스에만 전달합니다. 화면 입력으로 키를 저장하지 않고, 프로그램 파일에 키를 기록하지 않습니다.
- 비밀 입력을 지원하지 않거나 입력이 리다이렉트된 경우 키를 노출하는 일반 입력으로 전환하지 않고 중단합니다. 취소/잘못된 입력은 서버를 실행하지 않습니다.
- 이전 무료 서버를 종료한 뒤 같은 127.0.0.1:8012 주소로 실행합니다. 실제 AI 관심사 분석 버튼을 명시적으로 누를 때만 API를 호출합니다. Gemini 무료 API로 바꾼 기능이 아닙니다.
- 키/데이터 폴더 환경 변수는 실행 중에만 설정하고 종료 시 기존 값을 복원합니다. 전역 PC 설정과 Codex 시크릿은 수정하지 않습니다.
- Python 테스트 61개 통과. 새 6개 검사는 비용 동의 취소, 비터미널 입력 거절, 비밀 입력 미지원 중단, 빈/공백 키 거절, 환경 변수 복원, 예외 메시지의 키 노출 방지를 확인합니다. Windows에서 실제 두 번 클릭한 검증은 미실행이며 실제 유료 호출도 하지 않았습니다.
- docs/TESTING_FOR_TEACHERS.md에 최신 ZIP 업데이트·실행·키 발급·AI 초안 확인/확정·무료 실행으로 복귀하는 순서를 기록했습니다.

## 2. 서비스가 동작하는 원리

### 지금 공개된 기능

학생 입력 → 브라우저 JavaScript → 미리 수집한 제목 목록 검색 → 관련 제목과 원문 링크 표시

- HTML은 화면 틀, CSS는 디자인, JavaScript는 입력·화면 전환·저장을 담당합니다.
- 제목 검색은 공백과 기호를 정리하고 연속된 글자와 구절이 겹치는 정도를 비교합니다.
- 지도논문은 기본 검색에서 제외하며 사용자가 포함하도록 선택할 수 있습니다.
- 사용자 기록은 브라우저 localStorage에 저장합니다. 다른 기기와 자동 동기화되지 않습니다.

### 개발한 AI 평가 흐름

아이디어·학년·예산·기간·장비·관심사 → Python 서버 → 관련 제목 검색 → OpenAI Responses API → 결과 형식과 출처 검증 → 점수 계산·저장 → 화면 표시

- 이름과 API 키는 AI 요청의 학생 입력에 포함하지 않습니다. API 키는 서버에서 인증에만 사용합니다.
- OpenAI가 점수와 이유를 제안하고, 서버가 점수 범위·아이디어 번호·출처 ID를 검사합니다.
- 평균, PASS 여부, 상위 후보 선정은 일반 코드로 계산합니다.
- PASS는 평균이 설정한 기준값보다 큰 경우입니다.
- 통과 후보가 3개 미만이면 보완 안내를 표시합니다. 자동 생성·재평가는 아직 구현 전입니다.
- 평가 결과는 개발 서버의 SQLite에 저장하며 동일 조건 결과를 24시간 재사용합니다. 실제 모델 성공 결과의 저장·재사용도 크레딧 충전 후 검증했습니다.

### 선택한 모델과 평가의 한계

- 초기 평가 모델 기본값: `gpt-4.1-mini` (설정으로 변경 가능)
- 임베딩 기본값: `text-embedding-3-small`
- 최신 또는 가장 정확한 모델이라고 단정하지 않으며, 실제 사례의 품질·비용 검증 후 조정합니다.
- 현재 근거는 주로 제목입니다. 실험 방법 중복이나 표절 여부를 확정할 수 없습니다.
- 수상 확률을 예측하는 모델을 학습시킨 것이 아닙니다. 공식 심사 기준도 아직 별도로 입력하지 않았습니다.

처음 기획은 아이디어 선정부터 실험, 보고서, 제출 관리까지 포함했습니다. 첫 개발에서는 사용 흐름을 검토할 수 있도록 앞부분을 먼저 구현했습니다.

## 3. 어떤 원리로 만들었나요?

### 화면 → 상태 → 저장

앱은 사용자의 입력을 JavaScript 객체에 보관합니다. 이 객체를 '상태(state)'라고 부릅니다.

상태에는 현재 단계, 이름, 학년, 예산, 기간, 아이디어 목록, 선택한 주제, 선행 연구 메모, 실험 기록이 들어갑니다.

예를 들어 사용자가 후보를 선택하면 다음 일이 일어납니다.

1. 선택한 후보를 상태에 넣습니다.
2. 현재 단계를 '실험 계획'으로 바꿉니다.
3. 상태를 브라우저 저장 공간에 기록합니다.
4. 상태에 맞는 화면을 다시 그립니다.

주소가 여러 페이지로 바뀌는 방식이 아니라, 하나의 HTML 안에서 단계에 따라 화면 내용을 바꾸는 구조입니다.

### HTML·CSS·JavaScript의 역할

| 기술 | 쉬운 설명 | 이 앱에서 맡은 일 |
| --- | --- | --- |
| HTML | 화면의 기본 틀 | 메뉴, 본문, 안내 문구, 스크립트 연결 |
| CSS | 화면의 디자인 | 색상, 카드, 버튼, 여백, 모바일 배치 |
| JavaScript | 사용자의 행동에 반응하는 기능 | 입력, 화면 전환, 후보 선택, 저장, 다운로드 |

React나 Next.js 같은 프레임워크 없이 브라우저 기본 기술로 만들었습니다. 첫 화면 흐름을 빠르게 검토하는 규모에서는 별도 패키지 설치 없이도 구현할 수 있기 때문입니다.

앞서 Next.js·Python·데이터베이스 구성을 제안했지만, 그것은 실제 AI 서비스로 확장할 때의 후보 구성이었습니다. 이번 프로토타입에 그 구성을 구현한 것은 아닙니다.

## 5. 평가 점수는 어떻게 나오나요?

현재 점수는 AI가 아이디어 내용을 판단한 결과가 아닙니다. 아이디어의 입력 순서에 따라 정해진 예시 숫자를 만들어 화면 흐름을 확인합니다.

현재 화면의 네 가지 기준:

- 차별성
- 대회 기준 적합도
- 현실화 가능성
- 관심사 관련성

네 점수의 평균을 반올림해 높은 순으로 최대 3개를 보여줍니다. 아이디어가 하나면 후보도 하나만 보여줍니다.

'수상 가능성' 대신 '대회 기준 적합도'라는 표현을 사용했습니다. 수상작만으로 실제 수상 확률을 검증하기 어렵기 때문입니다. 현재는 이 적합도 역시 예시입니다.

실제 서비스에서는 수상작 자료, 심사 기준, 학생의 조건 등을 이용하는 평가 서비스로 이 부분을 교체해야 합니다.

## 6. 입력 데이터는 어디에 저장되나요?

현재는 브라우저의 `localStorage`를 사용합니다. 같은 브라우저에서 새로고침해도 데이터를 다시 불러올 수 있는 저장 공간입니다.

- 저장 키: `jlh-project-v1`
- 저장 형식: JSON
- 입력할 때 자동으로 저장을 시도합니다.
- 저장 공간 부족 등으로 저장하지 못하면 안내 문구를 표시합니다.
- JSON 다운로드 버튼으로 프로젝트 데이터를 파일로 보관할 수 있습니다.

### 현재 저장 방식의 의미

- 입력 내용이 GitHub 저장소에 올라가는 것은 아닙니다.
- 이 앱의 기록 저장 기능은 별도 서버로 입력 내용을 전송하지 않습니다.
- 다른 컴퓨터나 다른 브라우저와 자동으로 동기화되지 않습니다.
- 브라우저 데이터를 지우면 기록도 사라질 수 있습니다.
- 현재 JSON 파일을 다시 가져오는 복원 기능은 없습니다.
- 공동 사용 기기에서는 같은 브라우저의 기록을 다른 사람이 볼 수 있으므로 별명과 예시 데이터로 체험하는 편이 좋습니다.

선생님이 여러 학생을 관리하려면 이후 로그인과 서버 데이터베이스가 필요합니다.

## 7. 개발은 어디에서 했나요?

Codex가 제공하는 원격 작업용 컴퓨터에서 개발했습니다. 이것을 대화에서 '클라우드 개발 환경'이라고 불렀습니다.

그 컴퓨터의 `/workspace/jlh` 폴더가 연결된 GitHub 저장소의 작업 폴더입니다. 사용자의 개인 PC에 자동으로 파일을 내려받아 작업한 것은 아닙니다.

개발 중에는 다음 명령으로 임시 웹 서버를 실행했습니다.

```sh
cd /workspace/jlh
npm start
```

실제로 실행되는 명령:

```sh
python3 -m http.server 3000 --bind 0.0.0.0
```

Python이 파일을 웹 브라우저에 전달하는 간단한 서버 역할을 했습니다. AI 서버나 데이터베이스 서버를 만든 것은 아닙니다.

`localhost:3000`은 브라우저가 실행되는 컴퓨터의 3000번 포트를 의미합니다. 사용자 PC와 Codex의 원격 컴퓨터는 다르므로, 사용자 쪽 브라우저에서 같은 주소를 입력한다고 원격 앱에 연결되는 것은 아닙니다. 초기 접속 안내에서 이 차이를 충분히 설명하지 못했고, 이후 공개 주소를 만들어 해결했습니다.

## 9. GitHub에는 어떻게 저장했나요?

Git은 코드 변경 이력을 관리하는 도구이고, GitHub는 그 저장소를 온라인에 보관하는 서비스입니다.

작업 순서:

1. 원격 저장소에 기존 브랜치·커밋이 없는 상태를 확인했습니다.
2. 작업 폴더에 웹앱 파일을 만들었습니다.
3. 테스트를 실행했습니다.
4. 파일들을 Git에 추가했습니다.
5. 첫 커밋으로 변경 이력을 남겼습니다.
6. GitHub의 `main` 브랜치로 푸시했습니다.

실행한 핵심 명령:

```sh
git add README.md app.js index.html model.mjs package.json style.css tests
git commit -m 'Build science inquiry prototype with idea selection and experiment notes'
git push origin HEAD:main
```

로컬 작업 브랜치 이름은 `work`였고, 그 내용을 원격의 `main`에 올렸습니다.

- 커밋: 현재 변경 내용을 하나의 이력으로 기록
- 푸시: 로컬의 커밋을 GitHub로 전송

## 10. 웹사이트 배포는 어떻게 했나요?

현재 앱은 HTML·CSS·JavaScript 파일만으로 동작하므로 GitHub Pages를 사용했습니다. GitHub Pages는 저장소의 파일을 인터넷에서 열 수 있는 웹사이트로 제공하는 서비스입니다.

배포 순서:

1. 코드를 GitHub `main`에 올렸습니다.
2. Codex에서 Pages 설정을 생성하려 했지만, 연결된 GitHub 권한으로는 설정 변경이 허용되지 않아 HTTP 403을 받았습니다.
3. 사용자가 저장소의 Settings → Pages에서 직접 설정했습니다.
4. Source는 `Deploy from a branch`, Branch는 `main`, 폴더는 `/ (root)`로 지정했습니다.
5. GitHub가 사이트를 빌드하고 배포했습니다.
6. 배포 성공과 공개 파일 응답을 확인했습니다.

공개 주소:

https://swcroh926.github.io/jlh/

개발 중 사용했던 Python 서버는 공개 사이트 운영에 필요하지 않습니다. 공개 사이트의 파일은 GitHub Pages가 제공합니다. Codex 작업 환경이 중지되어도 GitHub Pages 사이트는 별도로 운영됩니다.

## 12. 앞으로 수정하면 어떻게 반영되나요?

기획 변경 → 코드 수정 → 테스트 → 커밋 → `main`에 푸시 → GitHub Pages 자동 배포 → 공개 주소 확인

현재 설정을 유지하면 `main`에 새 코드를 올릴 때 GitHub Pages 배포가 이어집니다. 작업 폴더에서 파일만 수정하고 푸시하지 않으면 공개 사이트는 바뀌지 않습니다.

## 13. 실제 AI 서비스로 발전시키려면

다음 단계는 구현 예정안이며, 현재 완성된 기능이 아닙니다.

1. 수상작 자료 확보와 구조화: 제목·연구 질문·실험 방법·결과·출처 등을 정리합니다.
2. 검색 기반 평가: 관련 작품을 찾아 중복·차별점과 평가 근거를 제시합니다.
3. AI 서버 연결: 브라우저가 서버에 요청하고 서버가 AI를 호출하도록 구성합니다. API 비밀키를 공개 JavaScript에 넣지 않습니다.
4. 학생·프로젝트 데이터베이스: 여러 기기에서 기록을 이어가고 선생님이 학생별 프로젝트를 관리할 수 있게 합니다.
5. 실제 연구·구매처 검색: 확인한 출처와 조회 시점을 함께 보여줍니다.
6. 주제별 실험 설계와 검토: 학년·장비·기간·예산을 반영하고 선생님이 검토하는 흐름을 만듭니다.
7. 문서 입력·보고서 출력: DOCX·HWP 지원과 보고서 양식을 확장합니다.

GitHub Pages는 정적 파일 제공에 적합합니다. 비밀키를 사용하는 AI 호출과 데이터베이스 처리를 위해서는 별도 서버 또는 서버리스 서비스가 추가로 필요합니다.

## 14. 현재 결과 요약

완료: 화면 뼈대, 기본 사용자 흐름, 브라우저 저장, 기본 테스트, GitHub 저장, GitHub Pages 공개 배포.

미완료: 실제 AI 판단, 수상작·선행 연구 검색, 주제별 실험 설계, 로그인, 서버 데이터 저장, 보고서 생성.

현재 버전의 목적은 실제 평가 성능을 검증하는 것이 아니라, 사용자가 화면을 직접 사용하며 서비스 흐름과 필요한 기능을 구체화하는 것입니다.
